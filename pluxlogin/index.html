PluxLogin 登录注册插件

高性能、高安全 Minecraft 登录注册插件：BCrypt 密码渐进升级 / AES-256-GCM 字段加密 / AuthMe 导入 / 本地网页管理 / REST API。兼容 1.7.10 ~ 26.3+，Spigot / Paper / Purpur / Folia。

作者：aya_xzer21145 数据库：SQLite / MySQL Java：8+ 安全：BCrypt + AES-256-GCM

2.1.0 更新主题

本次是架构与安全大版本：有界异步执行架构、原生 Folia 调度、配置快照化、BCrypt + 渐进式重哈希、AES-256-GCM 字段加密、REST API v1、本地网页控制台、AuthMe 三阶段导入、游戏内 GUI 全面升级。

功能特性

🔐

登录/注册系统

基础账号密码登录注册，密码默认 BCrypt（cost 12）。

🔄

渐进式密码哈希升级

旧 PluxLogin 无盐 SHA-256、AuthMe $SHA$ / BCrypt / PBKDF2 用户首次登录自动重哈希为 BCrypt。

🎫

验证码系统

注册前需完成验证码验证，防止恶意注册。

📧

邮箱绑定

支持邮箱绑定、找回密码，敏感字段 AES-256-GCM 加密存储 + HMAC 盲索引。

🐧

QQ 绑定

支持 QQ 号绑定与 QQ 邮箱找回密码，敏感字段 AES-256-GCM 加密存储。

🔑

双因素认证 2FA/TOTP

基于 TOTP 的二次验证，密钥加密存储。

🖥️

游戏内 GUI 管理

可视化仪表盘、玩家管理、危险操作 CAS 二次确认、AuthMe 导入子页。

🌐

REST API v1

Bearer 鉴权、固定窗口限流、revision CAS、分页查询。

🏠

本地网页控制台

插件内置 HTTP 服务，仅回环地址，独立管理员凭据，CSRF + 会话过期保护，无外部 CDN。

📥

AuthMe 导入

dry-run → 确认令牌 → 真实导入三阶段，支持 SQLite 与 MySQL 远端。

🤖

反机器人系统

快速加入检测、临时封禁，抵御机器人攻击。

⚡

有界异步架构

DB / 密码 / 邮件 / HTTP 四线程池独立，固定 AbortPolicy 不阻塞服务器线程。

🧵

Folia 原生兼容

PlatformScheduler 统一 Bukkit/Folia 调度，全局/玩家任务自动选择正确线程。

💾

多数据库支持

SQLite（WAL + busy_timeout）与 MySQL（HikariCP 连接池）。

安装

  1. 下载最新版本 PluxLogin-2.1.0.jar。
  2. 将插件放入服务器 plugins/ 文件夹。
  3. 启动服务器，自动生成 settings.yml / messages.yml / gui.yml / actions.yml / security/keys.yml。
  4. 首次启动后立即备份 plugins/PluxLogin/security/keys.yml（AES 主密钥，丢失后敏感字段无法解密）。
  5. 按需修改 settings.yml 配置。
  6. 执行 /pluxlogin reload 重载配置。

旧版本升级（2.0.x → 2.1.0）

  • 旧 config.yml 自动迁移到 settings.yml，旧文件保持并备份到 backups/。
  • 旧 message.yml 自动迁移到 messages.yml。
  • 旧 welcome.txt / join.txt 自动迁移到 actions.yml。
  • 密码字段保持旧格式；用户首次登录时自动重哈希为 BCrypt。

编译

mvn clean package
# 产物：target/PluxLogin-2.1.0.jar

升级后立即执行的安全清单

  1. 将 plugins/PluxLogin/security/keys.yml 与数据库一起离线备份。
  2. 旧密码用户首次登录会被重哈希为 BCrypt，无需管理员干预；想强制全部用户升级可在低峰期让活跃玩家登录一次。
  3. 启用 REST API 时务必配置 ≥ 32 字符的 api.secret，默认监听 127.0.0.1，外网请走反代 + TLS。
  4. 本地控制台首次使用需执行 /pluxlogin console setup 生成凭据。
  5. AuthMe 导入前务必备份源库与 PluxLogin 当前数据库。

核心功能

登录状态机

登录/注册/验证码/绑定状态严格单调，不允许跳步和反向迁移：

LOADING → CAPTCHA/REGISTER/LOGIN → AUTHENTICATING → TOTP_VERIFY/FORCE_EMAIL → AUTHENTICATED

密码与哈希

  • 新注册用户密码统一写入 BCrypt（cost 钳制 10–14）。
  • 验证时兼容以下历史格式，成功后 CAS 原子重哈希为新 BCrypt：
    • 旧 PluxLogin 无盐 SHA-256
    • AuthMe $SHA$ 加盐格式
    • AuthMe BCrypt（$2a$ / $2b$ / $2y$）
    • AuthMe PBKDF2
  • credential_version 字段记录当前密码算法版本。

敏感字段加密

  • 邮箱、QQ、TOTP 密钥使用 AES-256-GCM 加密存储（随机 12 字节 IV、128 字节 Tag，UUID + 字段名作为 AAD）。
  • 邮箱 / QQ 额外生成 HMAC-SHA256 盲索引（email_lookup / qq_lookup），用于绑定冲突检测时不暴露明文。
  • 邮箱冲突时密文仍加密保存，盲索引置 NULL。
  • 主密钥存储于 security/keys.yml，插件首次启动自动生成并打印备份提醒。

2FA / TOTP

  • /2fa on / /2fa off 管理双因素认证；/2fac <验证码> 验证。
  • TOTP 密钥使用 AES-256-GCM 加密存储。
  • 2.1.0 修复了 TOTP 验证成功后重复进入验证态的死循环。

邮箱 / QQ 绑定

  • 命令：/mail <邮箱> → /mailc <验证码>；/qq <QQ号> → /qqc <验证码>。
  • 绑定冷却：请求验证码受冷却限制，并发请求被 inFlight 标记拦截。
  • 邮箱验证码通过 SMTP 发送；465 端口自动启用隐式 SSL（SMTPS），其余端口走 STARTTLS。

找回密码

  • /mailzhpass：通过邮箱重置密码。
  • /qqzhpass：通过 QQ 重置密码。
  • /resetpass：未登录状态通过邮箱/QQ/2FA 重置密码。

游戏内 GUI 管理

  • 总览仪表盘：注册数、活跃玩家、数据库类型、加密状态、运行时长。
  • 分页玩家列表、玩家详情面板、审计日志查看。
  • 危险操作（删除账号、解绑邮箱/QQ、关闭 2FA、重置密码）：需 10 秒一次性确认按钮点击后才执行，并走 revision CAS。
  • AuthMe 子页：对 plugins/AuthMe/authme.db 一键 dry-run、查看报告、提交确认令牌；自定义 MySQL 来源引导至本地网页（避免在聊天中暴露数据库密码）。
  • 跨版本兼容：Material.matchMaterial 字符串查找，缺失时降级为 PAPER，老版本不再崩 GUI。

欢迎动作系统（actions.yml）

替代旧 welcome.txt / join.txt，支持两个触发点：

  • join：玩家加入时触发。
  • authenticated：玩家登录成功后触发。

动作类型：[COMMAND]（全局调度执行）、[TP] / 消息（每玩家调度），原生 Folia 兼容。

config-version: 1
join:
  - "[COMMAND] say {player} 进来了！"
authenticated:
  - "[TP] 0 100 0 world"
  - "[MESSAGE] &a欢迎 {player} 回来！"

反机器人系统

  • 快速加入检测：anti-bot.min-interval 间隔低于阈值判定为可疑。
  • 临时封禁：anti-bot.temp-ban-duration 秒内禁止重入，提示 login.temp-ban-kick（含 {time}）。
  • 踢出惩罚链：security.kick-command 支持列表写法，同时替换 {player} 与 %player%。

数据库

  • SQLite：开启 WAL + busy_timeout=30s。
  • MySQL：HikariCP 连接池，支持 SSL；verifyServerCertificate 随 ssl=true 同时开启。
  • 查询统一超时 30s，分页上限 500。

更新检查器

  • 后台定时检查，登录链路不再发起 HTTP 请求（读取缓存 getLatestVersion()）。
  • 读空响应不再 NPE，连接与缓冲流 try-with-resources，超时 30s→10s。
  • 移除了全局关闭 TLS 主机名校验的危险设置。
  • update-checker.enabled 可开关。

storage:

  revision: 1
  sqlite:
    path: "plugins/PluxLogin/data.db"
  mysql:

    port: 3306
    database: pluxlogin
    username: root

password-policy:
  min-length: 6
  max-length: 32                  # UTF-8 编码后不得超过 BCrypt 72 字节上限
  pattern: "^[a-zA-Z0-9_!@#$%^&*]+$"
  bcrypt-cost: 12                 # 安全范围 10-14，超出配置拒绝启动

配置快照与校验

  • ConfigManager.validateAndPublish 整体校验四个配置文件后一次性发布字段。
  • 任何一份解析或校验失败 → 保留上一次完整快照并抛异常；首次启动直接 IllegalStateException 拒绝使用默认值覆盖安全策略。
  • mergeMissing 只向用户文件写入缺失键，用户已覆盖的值永不被重置。

安全校验（20+ 项）

  • BCrypt cost 必须在 10–14。
  • 密码最大长度 UTF-8 编码 ≤ 72 字节。
  • DB 线程 ≤ 16、密码线程 ≤ 8、队列 ≤ 4096、MySQL pool ≤ 32。
  • MySQL min-idle ≤ pool-size，SQLite 路径非空。
  • 认证超时 5–3600 秒、验证码长度 1–10。
  • API 启用时 secret ≥ 32 字符、CORS Origin 不能为 * 且必须带 http(s):// 协议。
  • 控制台 session-minutes 在 1–1440 之间。

安全架构

有界异步执行架构

原版本多数业务直接在命令线程/HTTP 线程同步执行密码哈希、数据库 I/O、邮件发送等阻塞操作，易导致主线程卡顿或 Folia Region 线程超时。

  • 新增 AsyncDatabaseExecutor，分离 DB / 密码 / 邮件 / HTTP 四个独立线程池。
  • 各自独立有界队列（默认 256 容量），拒绝策略固定 AbortPolicy，禁止 CallerRunsPolicy 阻塞服务器线程。
  • 关闭时按序停止 HTTP → 排空各池 → 关闭数据库，确保进程退出无残留。

统一调度抽象（Folia 兼容）

  • PlatformScheduler 通过反射在运行期识别 Folia，桥接 GlobalRegionScheduler / EntityScheduler。
  • 统一提供全局任务、每玩家任务、延迟任务、周期任务四个入口。
  • ConfigManager.executeActions、欢迎消息、Title/ActionBar 倒计时、邮件验证码发送、AuthMe 导入任务全部迁移到该抽象层。

密码存储：BCrypt + 渐进式重哈希

  • security/PasswordService 统一 BCrypt（cost 钳制 10–14）写入。
  • 验证时兼容旧格式；成功后通过 CAS（数据库 revision 递增）将旧格式一次性重哈希为新 BCrypt。
  • credential_version 字段记录当前密码算法。

敏感字段加密：AES-256-GCM + 盲索引

  • security/FieldEncryptionService 使用 AES-256-GCM（随机 12 字节 IV、128 字节 Tag、UUID + 字段名作为 AAD 绑定密文与玩家）。
  • 密钥存储在 security/keys.yml，首次启动自动生成并打印备份提醒。
  • 邮箱 / QQ 额外生成 HMAC-SHA256 盲索引，用于绑定冲突检测时不暴露明文。

危险管理操作 CAS 保护

原版本 /regdel、改密、解绑邮箱/QQ、关闭 2FA 等管理操作在 precheck 与写库之间存在竞态窗口。

  • DatabaseManager 为密码、邮箱、QQ、TOTP 密钥、玩家删除新增 updateXxxStrict(..., long expectedRevision) / deletePlayerStrict(UUID, long expectedRevision) 签名。
  • 原子地在 WHERE revision=? 条件下更新并自增 revision；返回受影响行数（0 表示 revision 已变，操作被拒绝）。
  • GUI 危险操作额外要求 10 秒一次性确认，本地网页要求输入完整玩家名二次确认，REST 要求携带当前 revision。

配置校验安全边界

  • BCrypt cost 放行 4–31 → 收紧为 10–14。
  • 线程池 / 队列 / 连接池上限强制。
  • MySQL min-idle 与 pool-size 关系校验。
  • API 启用时 secret 强度检查。
  • 越界配置在启动或 reload 时直接报错，拒绝应用。

Web API 安全加固

  • 密钥为空时直接返回 503，避免“忘配密钥即裸奔”。
  • 鉴权改为常数时间比较（MessageDigest.isEqual）抵御时序侧信道。
  • 响应输出流 try-with-resources、异常统一 500、exchange.close()。

CAS revision 危险操作

玩家数据上的危险操作（删除、重置密码、解绑邮箱/QQ、关闭 2FA）采用 compare-and-swap 保护：

  1. 先查询玩家，取 revision 字段（每次成功写库自增 1）。
  2. 提交修改时携带 expectedRevision。
  3. 服务端原子执行 UPDATE ... WHERE uuid=? AND revision=?；受影响行数为 0 时返回 409。
curl -X POST -H "Authorization: Bearer YOUR_SECRET" \
  -H "Content-Type: application/json" \
  -d '{ "expectedRevision": 5 }' \
  http://127.0.0.1:8701/api/v1/players/8f3a2c1d-e4f5-6789-0abc-def123456789/password-reset
{
  "success": true,
  "data": {
    "newPassword": "R7kX2mQ9vNp4",
    "newRevision": 6
  }
}

AuthMe 导入

采用 dry-run → confirm → execute 三阶段设计，避免误操作。统一由 AuthMeImportJobs 协调器管理，避免同一时间重复执行。

生命周期

[ dry-run 请求 ]
        ↓
  QUEUED → RUNNING → SUCCESS/FAILED   (报告候选/冲突/需重置数量)
        ↓   (5 分钟内)
[ confirm + token ]
        ↓
  新任务 QUEUED → RUNNING → SUCCESS/FAILED   (真正写入数据库)
  • 同一时间只允许一个 RUNNING 任务。
  • dry-run 完成后生成确认令牌，有效期 5 分钟。
  • confirm 必须携带正确 token 和 dry-run 的 jobId。
  • 完成的任务保留约 1 小时、上限 32 个。
  • 过期后需重新 dry-run。

支持来源

  • AuthMe SQLite 文件一键导入（默认路径 plugins/AuthMe/authme.db）。
  • AuthMe MySQL 远端导入（仅服务端控制台可提交密码）。
  • Reader 优先使用 AuthMe 原生 uuid / real_uuid 列，没有则回退到 OfflinePlayer:<name>。
  • MySQL 连接显式 setReadOnly(true) + JDBC URL readOnly=true。

密码算法识别

  • 覆盖 AuthMe 原生 $SHA$、BCrypt、PBKDF2。
  • 未知算法标记为“需重置”但不阻塞导入；玩家后续走邮箱/QQ 找回密码流程。

命令方式

# SQLite dry-run
/pluxlogin import authme dry-run sqlite plugins/AuthMe/authme.db authme

# MySQL dry-run
/pluxlogin import authme dry-run mysql 127.0.0.1 3306 authme_db readonly_user pass authme

# 确认导入
/pluxlogin import authme confirm <jobId> <token>

# 查询状态
/pluxlogin import authme status <jobId>

REST API 方式

# 1. 提交 dry-run
curl -X POST -H "Authorization: Bearer YOUR_SECRET" \
  -H "Content-Type: application/json" \
  -d '{
    "type": "sqlite",
    "sqlitePath": "plugins/AuthMe/authme.db",
    "table": "authme"
  }' \
  http://127.0.0.1:8701/api/v1/imports/authme/dry-run

# 2. 轮询任务，拿到 confirmToken

  http://127.0.0.1:8701/api/v1/imports/a1b2c3d4e5f6

curl -X POST -H "Authorization: Bearer YOUR_SECRET" \
  -H "Content-Type: application/json" \
  -d '{ "sourceJobId": "a1b2c3d4e5f6", "confirmToken": "xK9mP2qZ..." }' \
  http://127.0.0.1:8701/api/v1/imports/authme/confirm

字段说明

常见问题

Q1：升级到 2.1.0 后配置去哪了？

旧 config.yml / message.yml / welcome.txt / join.txt 会在首次启动时自动迁移到 settings.yml / messages.yml / actions.yml，旧文件保持并备份到 backups/ 目录。可随时对比或回退。

Q2：security/keys.yml 丢了怎么办？

该文件是 AES-256-GCM 主密钥，丢失后邮箱/QQ/TOTP 密文无法解密。必须在首次启动后立即与数据库一起离线备份，并加入 .gitignore。跨主机迁移时先拷密钥再拷数据库。

Q3：REST API 启动报 secret 错误？

api.secret 长度必须 ≥ 32 字符，否则启动即拒绝。生成命令：openssl rand -hex 24。

Q4：API 返回 401 / 429 / 409？

401：检查 Authorization: Bearer 拼写；常数时间比较导致不匹配时不会告诉你差在哪。429：超过 api.rate-limit 窗口。409：revision 已变，重新查询玩家拿新 revision 再提交。

Q5：本地控制台静默不启动？

security/console.yml 不存在。执行 /pluxlogin console setup 生成凭据；控制台启动失败不会拖垮登录插件。

Q6：控制台访问被拒绝？

控制台只允许回环地址访问。请在服务器本机浏览器打开 http://127.0.0.1:8702，或走 SSH 隧道：ssh -L 8702:127.0.0.1:8702 server@your-host。

Q7：AuthMe dry-run 失败？

常见原因：源库文件不存在、MySQL 账号无读权限、表缺少 username / password 列。请检查路径、账号权限和表结构。

Q8：AuthMe confirm 提示 token 过期？

确认令牌有效期 5 分钟。过期后重新发起 dry-run 获取新 token。

Q9：旧 PluxLogin 用户需要重新注册吗？

不需要。旧无盐 SHA-256 密码在首次登录时验证通过后自动 CAS 重哈希为新 BCrypt，管理员无需干预。想强制全部用户升级，可在低峰期让所有活跃玩家登录一次。

Q10：AuthMe 导入后部分玩家无法用原密码登录？

dry-run 报告中 requiresReset > 0 的账号表示其源密码算法不识别（如 AuthMe 自定义哈希），导入后玩家需走邮箱/QQ 找回密码流程。

Q11：服务器是 Folia，能用吗？

能。2.1.0 起 PlatformScheduler 通过反射在运行期识别 Folia 并桥接 GlobalRegionScheduler / EntityScheduler，登录/绑定/验证码/欢迎动作等行为与 Bukkit/Paper 表现一致。

Q12：配置文件损坏会导致插件半启动吗？

不会。2.1.0 起 validateAndPublish 整体校验四份配置后一次性发布；任何一份失败都保留上一次完整快照并抛异常，首次启动直接 IllegalStateException 拒绝使用默认值覆盖安全策略。

Q13：支持 Minecraft 26.x 新命名体系吗？

支持。2.0.3 起 VersionUtil 原生识别 26.x / 26.x.y，并对仍写作 1.26.x 的别名做归一化（1.26.3 → 26.3）。新增 isAtLeast_26_3() 与通用 isAtLeast(major, minor)。

Q14：2FA / 强制邮箱门控可用吗？

2.1.0 保留代码但未接入登录链路（handlePostLogin 未被 completeLogin 调用）。贸然接入会使已开启 2FA / 强制邮箱的玩家卡在验证态。待后续版本完善后再启用。

Q15：Utils.hashPassword 仍是无盐 SHA-256 吗？

2.1.0 起新注册用户与登录后重哈希统一走 BCrypt（PasswordService），旧无盐 SHA-256 仅作为历史格式兼容验证。改加盐会使现有数据库密码全部失效，需配套渐进式重哈希（已实现）。

Q16：/regdel 会删错人吗？

不会。2.0.2 起改为直接 DELETE FROM players WHERE uuid=?，不再按 username 查询，避免改名后命中旧行。2.1.0 起进一步走 deletePlayerStrict(UUID, expectedRevision) CAS 保护。

Q17：mail 465 端口发不出验证码？

2.0.2 起 465 端口自动启用隐式 SSL（SMTPS），其余端口走 STARTTLS。按默认配置即可正常收发邮件。

Q18：如何把 API / 控制台暴露到公网？

不建议直接暴露。api.bind-address 与 console.bind-address 都应保持 127.0.0.1，通过 Nginx 等反代 + TLS 终止。反代后仍需保持后端绑定回环地址。
